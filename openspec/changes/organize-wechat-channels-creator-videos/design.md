## Context

当前仓库已经有两类相关沉淀：

- `Clippings/视频号/`：保存单条 `微信视频号` 剪藏的原始 `Markdown`、`JSON` 元数据和封面图。
- `raw/A_AI-Content-Creator(AI 创作者)/`：保存创作者人物卡片。

现有 `channels-video-processor` 能从单条短链解析出作者昵称、头像和当前视频描述，但它调用的是单条内容接口，因此天然停留在“单视频上下文”。现在需求已经澄清：用户给出某个 `视频号` 视频，不是为了建立一个“平台视频目录”，而是为了把这个人蒸馏出来，后续还会继续补充同一人的 `公众号`、`书籍` 和其他资料。新的设计必须从“平台中心”切换成“人物中心”。

同时，用户对采集阶段的要求已经升级：不希望再依赖“手动打开某个具体视频再下载”的逐条操作，而是希望系统从任意一条 `视频号` 链接出发，尽量自动找出该创作者的全部视频入口，批量下载或批量登记，再继续蒸馏。最终产物也不应停在人物档案本身，而应能进一步编译成一个面向该创作者的个人理解 `skill`。

约束如下：

- 仓库是知识库，不是业务服务，产物优先是 `Markdown`、`JSON` 和静态素材，而不是在线接口。
- `raw/` 层强调来源保真，不能把“整理结果”和“原始采集”混写到一个文件里。
- `微信视频号` 页面与接口存在漂移风险，设计上必须允许先保留原始抓取结果，再做规范化整理。

## Goals / Non-Goals

**Goals:**

- 定义如何用单条内容链接或单个平台资料作为 seed，归并出统一的人物实体。
- 定义如何从单条 `视频号` seed 继续发现同一创作者的内容列表，并记录枚举覆盖度与失败点。
- 规定多源资料至少应产出哪些层次的文件，包括原始来源、证据清单和人物蒸馏结果。
- 规定批量采集阶段如何处理下载成功、下载失败、未下载、时间不精确等证据完整性问题。
- 让同一个人可以持续补充来自不同平台和媒介的材料，而不会裂变成多份独立档案。
- 让人物资料页、来源清单和蒸馏结论之间形成稳定关联，便于后续继续追加证据或修正判断。
- 规定如何把蒸馏后的人物档案继续编译成一个可复用 `skill`。

**Non-Goals:**

- 本次不要求一次性打通所有平台的自动抓取。
- 本次不要求对每一条视频、文章或书籍都自动完成高质量全文理解。
- 本次不把人物蒸馏结果直接提升到 `wiki/` 的最终知识页面；先保证 `raw` 层人物档案是稳定可迭代的。
- 本次不承诺仅依赖公开网页接口就能稳定拿到某个创作者的全部 `视频号` 内容；若公开路径不足，可以退化为 `Mac WeChat` 自动化采集，但目标仍然是不手工逐条点开。

## Decisions

### 1. 采用“人物主档 + 多源证据 + 蒸馏结果 + skill 编译”的四层结构

一次人物蒸馏拆成四层：

- 人物主档：保存在 `raw/A_AI-Content-Creator(AI 创作者)/`，描述这个人是谁、在哪些平台活跃、目前已知有哪些来源。
- 原始证据层：保留在 `Clippings/` 或 `raw/` 中的来源化文件，保存原始 `JSON`、文章、摘录、封面、页面快照或中间清单。
- 原始证据层：保留在 `Clippings/` 或 `raw/` 中的来源化文件，保存原始 `JSON`、文章、摘录、封面、页面快照、中间清单以及可获得的本地视频文件。
- 蒸馏结果层：落到人物主档的配套结构中，沉淀核心主题、反复出现的观点、方法论、代表内容和阶段性判断。
- `skill` 编译层：在人物档案已经稳定后，输出一个可复用的 `skill` 包，至少包括 `SKILL.md`、参考资料索引和蒸馏说明。

这样做的原因是知识库要同时满足四件事：认人、追证据、做判断、复用方法。只做平台目录无法把多源资料汇总到同一个人；只做最终总结又会失去来源可追溯性；只做人档而不做 `skill` 编译，后续仍要人工二次加工。

备选方案：

- 只保留平台级目录：实现简单，但后续 `公众号` 和 `书籍` 无法自然并入。
- 直接把所有来源和观点都写进单个人物文件：阅读上直观，但很快会膨胀并混淆“证据”和“结论”。
- 只做人档，不继续产出 `skill`：能沉淀知识，但无法直接变成后续可调用资产。

### 1.1 视频类来源优先保留本地媒体副本

对于 `视频号` 这类视频来源，若运行时能够获得本地视频文件，则本地视频副本属于高优先级证据，应与封面、元数据和摘录一起落盘。只有在确实无法下载视频时，才退化为“仅保存元数据与其他证据”。

这样做的原因是人物蒸馏后续往往需要重新核对原话、时间语境和表达方式，仅靠标题、描述或摘要不够稳。本地视频副本能支撑后续转写、复核和二次提取。

备选方案：

- 只保存在线链接：轻量，但链接失效或平台变化后无法复核。
- 一律不下载视频，只保存文本摘录：会损失大量原始语境和复查能力。

### 2. 创作者全量内容枚举采用“公开路径优先，客户端自动化兜底”的混合策略

从任意单条 `视频号` `seed` 出发，系统先尽量通过公开可见页面、公开接口响应、短链上下文和页面中的创作者线索，解析出创作者身份与内容列表入口；若公开路径无法稳定给出完整列表，则允许退化到 `Mac WeChat` 客户端自动化采集，但该自动化目标是批量遍历创作者主页或内容列表，而不是要求人工逐条点开每个视频。

原因是当前两个参考方向各自只解决了半个问题：

- 类似 `wx_channels_download` 的方案偏向“已打开单视频后的下载”。
- 类似“某个创作者专用 `skill`”的方案偏向“抓到资料后的总结整理”。

而用户真实目标是两者之间再补一层：从一个 `seed` 找到这个人完整内容面，再进入批量下载与蒸馏。

备选方案：

- 只依赖公开网页/接口：实现最干净，但对 `视频号` 这种漂移较大的平台风险高。
- 完全依赖人工在 `Mac WeChat` 里逐条点开：理论可行，但成本太高，不符合需求。
- 完全依赖桌面自动化而不做公开解析：能做，但前置定位成本更高，也不利于留存抓取证据。

### 3. 以人物实体作为主键，而不是以平台账号作为主键

后续所有来源都先回答“这是谁”，再回答“这条内容来自哪里”。人物主档继续沿用 `raw/A_AI-Content-Creator(AI 创作者)/AI 创作者 - <名称>.md` 这一现有模式，但主档中的平台链接、来源记录和蒸馏结果都围绕同一个人物实体组织。

这样可以把“人是谁”和“此人在哪儿说过什么”分开维护：

- 人物卡片更稳定，适合长期引用。
- 来源清单和证据清单变化频繁，适合持续增量更新。

备选方案：

- 以 `视频号`、`公众号`、`书籍` 各自维护独立主档：实现上最直接，但会把同一个人拆成多个平行节点。

### 4. 每个来源条目都必须同时保留“人物归并键”“来源追踪键”和“时间确定性”

每条来源条目同时保留三类关键信息：

- 人物归并键：用于把不同平台的内容稳定归并到同一个人。
- 来源追踪键：保存原始短链 `id`、文章链接、书名版本或抓取时拿到的原始唯一标识。
- 时间确定性：保存来源发布时间、发布时间精度以及该时间来自哪个字段或证据。

原因是后续不仅有 `视频号`，还会有 `公众号` 和 `书籍`。只保留平台来源键无法跨平台合并；只保留人物名又无法解释这条结论来自哪份证据。
而如果发布时间不清楚，后续做观点演化、时间线和“先后说法变化”时会失真。

备选方案：

- 只用人物名归并：容易把同名人物或品牌账号混淆。
- 只用来源键组织：会失去“这是同一个人”的统一视图。
- 只保留模糊发布时间文本：后续无法可靠排序和构建时间线。

### 5. 批量采集不是“全有或全无”，而是要显式记录覆盖度与失败原因

对创作者内容列表的枚举、下载和整理，不应把一次运行视为“成功 / 失败”二元结果，而要记录：

- 当次发现了多少条内容；
- 哪些条目成功下载了本地视频；
- 哪些条目只有元数据或封面；
- 哪些条目缺发布时间或只有模糊时间；
- 哪些条目因为页面限制、接口漂移或自动化失败而未完成。

原因是 `视频号` 平台天然存在不稳定性。如果不记录覆盖度和失败原因，后续就无法区分“这个人真的只有这么多内容”还是“这次采集只拿到了其中一部分”。

备选方案：

- 只保留成功条目：看起来整洁，但会伪造完整性。
- 采集失败直接终止整个人物流程：过于脆弱，无法支持逐步补料。

### 6. 首阶段以“可持续补料的人物档案 + 可编译 skill 资产”作为完成标准

第一阶段要求建立一份可持续补料的人物档案，并且档案内容已经具备继续编译成 `skill` 的稳定结构：能接收新的来源、能保留原始证据、能逐步补充这个人的核心观点和方法论，不要求一次性把所有来源都深度理解完。

原因是目录级结果已经能支撑：

- 判断一个人是否值得长期蒸馏。
- 先把高价值来源聚合到一起，再逐步做深入理解。
- 允许未来分批补充 `视频号`、`公众号`、`书籍` 而不推翻已有结构。
- 在资料足够时，直接把人物档案编译成一个面向该人的专用 `skill`。

备选方案：

- 一开始就追求“全量内容全自动总结”：成本高，而且在人物边界尚未稳定时容易返工。

## Risks / Trade-offs

- 平台资料风格差异大，自动归并可能误判 → 首阶段允许人工确认人物归并结果，再决定是否自动化。
- 同一个人可能存在多个账号、笔名或品牌化名称 → 主档中必须允许记录别名和平台身份线索。
- 证据层和蒸馏层混写会让结论不可追溯 → 设计上强制把来源清单与观点总结分开。
- 后续来源越来越多导致单文件过长 → 人物主档保持稳定摘要，把详细来源和证据索引拆到配套文件。
- 视频类来源有时无法稳定下载本地文件 → 允许降级保存元数据，但必须记录下载失败原因和当次证据完整度。
- 平台只暴露相对时间或模糊日期 → 需要单独记录时间精度，避免把估算时间当成精确发布时间。
- 创作者全量枚举可能无法 100% 公开完成 → 设计上允许公开抓取与客户端自动化并存，并把策略来源写入证据。
- `skill` 编译容易把“资料摘要”误写成“操作指令” → 需要单独定义 `skill` 输出结构，把证据、方法论和触发条件拆开。

## Migration Plan

1. 保留现有 `Clippings/视频号/` 单条剪藏内容不动。
2. 以已有创作者卡片为锚点，为人物蒸馏补充新的来源清单、内容枚举记录和证据组织方式。
3. 首次对某个人执行时，创建或补全该人物主档、来源记录、枚举记录和蒸馏结构。
4. 后续重复执行时，仅为该人物追加新来源或更新已有判断，不重复造册。
5. 当资料成熟后，再从人物档案编译出独立 `skill` 产物。

## Open Questions

- 人物主档中“来源清单”“证据索引”“蒸馏结论”最终拆成几个配套文件，需要结合首批样本的体量确认。
- 当同一个人跨平台名称不一致时，是否需要单独的人工确认映射步骤，需要在实施时结合真实样本决定。
- 视频号来源的发布时间最终以哪个字段为准，以及当页面只展示相对时间时如何补强，需要结合真实样本决定。
- 创作者主页或内容列表在 `视频号` 生态里是否始终能从公开 `seed` 稳定反推，需要结合真实样本持续验证。
- 未来 `skill` 产物应该固定落到哪个目录，是沉淀在当前仓库还是输出到独立 `skills` 仓库，需要实施时进一步定板。
