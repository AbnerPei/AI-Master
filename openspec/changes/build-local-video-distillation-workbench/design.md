## Context

当前仓库的强项在“整理输出”，例如：

- [scripts/creator_dossier.py](/Users/peijianbo/Documents/AbnerPei/AI-Master/scripts/creator_dossier.py)：把来源接入人物档案并生成 `Markdown` / `JSON` 结果；
- [视频号人物蒸馏工作流.md](/Users/peijianbo/Documents/AbnerPei/AI-Master/wiki/P_Playbooks(操作手册)/视频号人物蒸馏工作流.md)：定义了来源接入、证据记录和蒸馏输出的基本思路；
- [raw/source-manifest.md](/Users/peijianbo/Documents/AbnerPei/AI-Master/raw/source-manifest.md)：已经把 `raw/T_Transcripts(转录)/` 定义为转录类资料的自然落点。

但当前仓库缺少一个真正面向“本地视频文件”的可视化入口。用户的诉求不是再加一个命令行，而是：

- 用本地 `HTML` 做交互壳；
- 点击按钮后，底层去调本地 `Python` 脚本；
- 页面能看到任务现在跑到哪一步；
- 页面能实时看到 `log`；
- 结果落盘到用户自己选的目录，而不是仓库写死目录。

这意味着产品重点不是“做一个花哨前端”，而是把“交互层、执行层、产出层”拆干净。

## Goals / Non-Goals

**Goals:**

- 提供一个本地可视化工作台，支持选择单个本地 `mp4` 和输出目录。
- 让页面点击能够稳定触发本地视频处理任务，而不是手动复制命令。
- 以阶段化方式展示任务状态，至少覆盖输入校验、音频提取、转录、整理和写入。
- 让日志可追踪，可用于判断卡在哪一步、失败在哪里。
- 输出至少四类结果：`meta.json`、原始转录、清洗转录、`AI` 蒸馏结果。
- 明确转录来源和整理来源，避免最终文档失去 provenance。

**Non-Goals:**

- 本次不要求批量队列。
- 本次不要求多视频并发。
- 本次不要求页面内直接编辑文稿。
- 本次不要求第一版就强绑定某个固定知识库目录。
- 本次不要求一上来支持所有视频平台链接输入；第一版只处理本地 `mp4`。

## Decisions

### 1. 采用“三层结构”：`HTML` 壳、本地桥接层、`Python` 任务脚本

产品拆成三层：

- `HTML` 页面：负责表单、阶段展示、日志展示、结果预览和结果链接；
- 本地桥接层：负责把页面点击转换为本地任务启动、状态查询和日志流；
- `Python` 任务脚本：负责真正干活，包括音频提取、转录、清洗、`AI` 蒸馏和结果写入。

这样做的原因是：

- 纯静态 `HTML` 无法稳定地直接调用本地脚本；
- 让页面直接拼命令既脆弱也难维护；
- 把复杂性压到 `Python` 脚本层，更符合“底层用笨脚本做事”的预期。

备选方案：

- 纯 `HTML` + 前端本地能力：对本地脚本和文件系统支持太弱；
- 页面直接内嵌所有逻辑：会把 `UI` 逻辑和执行逻辑缠在一起；
- 只做命令行、不做页面：不满足用户对可视化和 `log` 展示的要求。

### 2. 任务流采用固定阶段，而不是黑盒长任务

第一版任务必须拆成可见阶段：

1. 输入校验
2. 音频提取
3. 文案提取
4. 文案清洗
5. `AI` 蒸馏
6. 结果落盘

页面显示时，至少要能区分：

- 尚未开始
- 运行中
- 成功
- 失败

这样做的原因是视频处理链路天然容易慢，也容易在 `ffmpeg`、本地 `ASR`、云端接口等环节失败。如果页面只显示“处理中”，用户没有办法判断任务到底卡在哪里。

### 3. 文案提取遵循“字幕优先、本地 `ASR` 其次、云端兜底”的顺序

虽然第一版输入是本地 `mp4`，仍然沿用之前已经验证过的顺序：

- 如果存在可复用的外挂字幕、嵌入字幕或已缓存字幕，优先直接使用；
- 如果没有可用字幕，优先走本地 `ASR`；
- 如果本地 `ASR` 不可用或失败，再走云端转录兜底；
- 如果仍然失败，也要生成带失败说明的结果，而不是静默无输出。

这样做的原因是：

- 已有字幕通常最便宜也最稳定；
- 本地 `ASR` 更符合“本地处理优先”的方向；
- 云端转录适合作为兜底，而不是默认主路径。

### 4. 页面必须同时展示“阶段进度”和“原始 `log`”

页面不能只有一个进度条。必须有两套信息：

- 阶段级状态，例如“`3/6 文案提取中`”；
- 原始日志流，例如“`16:43:12 本地 ASR 完成，耗时 38s`”。

这样做的原因是：

- 阶段状态适合快速理解任务位置；
- 原始 `log` 适合排查问题和判断细节。

两者缺一不可。

### 5. 输出目录由用户选择，但输出结构必须标准化

虽然用户可以自由选择输出目录，但每次任务的输出结构仍然需要标准化。第一版建议至少产出：

- `meta.json`
- `01-raw-transcript.md`
- `02-clean-transcript.md`
- `03-ai-distillation.md`

如有中间产物，也可以补充：

- `audio.wav`
- `job.log`
- `segments.json`

这样做的原因是：

- 用户需要目录选择自由；
- 系统需要稳定产物，后续才好接知识库、人物蒸馏或别的自动化流程。

### 6. `AI` 整理结果必须和原始转录分层保存

最终不能只保留一份“好看的摘要”。至少要分三层：

- 原始转录：保留尽量接近转录源的文本；
- 清洗转录：修正文案明显噪声、补齐基本分段；
- 蒸馏结果：抽取摘要、要点、结构化观点、行动项或方法论。

这样做的原因是：

- 本地 `ASR` 结果可能有噪声；
- 不能把带噪原稿直接当成最终笔记；
- 也不能只保留最终总结，否则后续无法复核。

### 7. 第一版只支持单任务闭环，不提前设计复杂调度

第一版只要求：

- 选择一个本地 `mp4`
- 选择一个输出目录
- 启动一个任务
- 页面看到状态和 `log`
- 拿到一套标准产物

暂不要求：

- 多任务并发
- 队列管理
- 任务取消
- 历史任务面板

这样做的原因是当前最值钱的是把单次闭环跑通，并把输入、日志、转录、整理、落盘的边界先定稳。

## Risks / Trade-offs

- 本地桥接层如果太薄，日志流能力可能不足；如果太厚，又会把很多业务逻辑重复一遍。
- 本地 `ASR` 对机器性能敏感，慢任务会放大页面状态设计的重要性。
- 云端转录和 `AI` 整理都会带来外部依赖，必须把失败原因回写到任务结果。
- 用户自选输出目录会增加路径校验和命名冲突处理复杂度。
- 如果后续要接入知识库固定目录，当前“自由输出目录”需要再加一层导入动作。

## Migration Plan

1. 先新增独立的本地视频蒸馏工作台变更，不改现有人物蒸馏脚本。
2. 先把“单本地 `mp4` -> 标准结果目录”闭环跑通。
3. 稳定后，再决定是否把产物导入 `raw/T_Transcripts(转录)/` 或接到人物蒸馏流程上。
4. 如果后续接知识库，再补一层“导入到当前仓库”的动作，而不是让第一版直接承担两套职责。

## Open Questions

- 本地桥接层最终采用什么最薄实现：轻量 `HTTP` 服务、桌面壳，还是别的本地宿主。
- 本地 `ASR` 默认模型、体积和首次初始化策略如何选。
- 结果预览是在页面内渲染 `Markdown`，还是只展示文件链接与摘要。
- 是否需要在第一版就记录任务历史，还是只做当前任务面板。
