# 如何创建、进化和使用自己的 Agent

## 这篇笔记要回答的问题

这不是一篇单纯介绍某个 Agent 产品的教程，而是我对“如何拥有一个真正属于自己的 AI Agent”的方法论草稿。

核心问题有三个：

1. 如何创建自己的 Agent？
2. 如何让这个 Agent 持续进化？
3. 如何在日常工作、学习、研究和知识库维护中真正用好这个 Agent？

这里的“自己的 Agent”不是指从零训练一个大模型，也不是只写一个固定 prompt，而是指把模型、工具、记忆、技能、知识库、工作流和个人偏好组合成一个长期可用、可迭代、能代替自己执行大量具体任务的 AI 工作伙伴。

## 我的初步结论

我理解的个人 Agent，本质上是一个“带工具、带记忆、带方法论、带执行环境的第二大脑操作系统”。

它应该具备几个特征：

- 能理解我的长期目标，而不是只回答单次问题。
- 能访问我的知识库、文件系统、Git 仓库、浏览器、终端和常用平台。
- 能把一次次成功经验沉淀成可复用流程，而不是每次从零开始。
- 能记住我的偏好、目录规范、命名规则、提交习惯和质量标准。
- 能在不确定时先检索、验证、对比，再输出结论。
- 能把外部资料转化为我的内部知识，而不是只做临时摘要。
- 能被我不断校正，并把校正结果转化为记忆、技能或知识库规则。

所以，创建 Agent 的关键不是“写一个万能提示词”，而是设计一个长期进化系统。

## 一、如何创建自己的 Agent

### 1. 先定义 Agent 的身份和边界

创建个人 Agent 的第一步，是明确它到底帮我做什么。

我不应该一开始就追求“全能 Agent”，而应该先定义几个高频场景：

- 知识库助手：导入资料、整理 raw、生成 wiki、维护 index/log/schema。
- 研究助手：搜索资料、对比观点、提炼方法论、形成可追溯结论。
- 写作助手：把零散想法扩展成结构化文章、提纲、脚本或卡片。
- 编程助手：读代码、改代码、跑测试、提交 Git、生成文档。
- 自动化助手：定时检查信息源、整理日报、触发工作流。
- 个人复盘助手：记录决策、总结失败、提炼下一步行动。

对我来说，Agent 的核心边界应该是：

- 不只是聊天，而是能执行。
- 不只是总结，而是能沉淀。
- 不只是调用工具，而是能形成流程。
- 不只是完成任务，而是能提升下一次完成任务的质量。

### 2. 选择一个可持续使用的 Agent 底座

底座至少包含五层：

1. 模型层：负责理解、推理、生成和规划。
2. 工具层：负责读写文件、搜索、浏览器、终端、Git、消息平台等外部动作。
3. 记忆层：保存长期偏好、环境事实、稳定规则。
4. 技能层：保存可复用工作流，例如“导入 B 站 AI 创作者资料”“整理 LLM Wiki 原文”。
5. 知识库层：保存可检索、可版本管理、可人工阅读的长期知识。

模型可以替换，工具可以扩展，但记忆、技能和知识库会越来越像我自己的资产。

因此，个人 Agent 不应该被绑定在某个单一聊天窗口里，而应该尽量运行在一个可配置、可迁移、可版本管理的环境中。

### 3. 给 Agent 准备个人上下文

Agent 能不能像“我的 Agent”，关键取决于它是否有足够清晰的个人上下文。

个人上下文包括：

- 我是谁：角色、领域、长期目标。
- 我怎么工作：常用目录、Git 习惯、文件命名、知识库结构。
- 我喜欢什么质量：细节要全、逻辑要细、不接受空泛总结。
- 我讨厌什么：乱改源目录、主动 push、过度抽象、丢失 provenance。
- 我有哪些长期项目：AI-Master、LLMWiki、A 股知识库、Schooldays 等。
- 我的知识库规范：raw/wiki/schema 分层、Obsidian、frontmatter、manifest、log。

这些上下文不应该全部塞进单次 prompt，而应该分层保存：

- 稳定偏好进入 memory。
- 可复用流程进入 skill。
- 领域知识进入 wiki。
- 原始资料进入 raw。
- 项目规则进入 SCHEMA.md、AGENTS.md 或仓库说明。

### 4. 给 Agent 配工具，而不是只给答案空间

Agent 与普通 ChatGPT 最大的区别，是它能操作外部世界。

一个可用的个人 Agent 至少需要：

- 文件工具：读、写、搜索、patch。
- 终端工具：运行脚本、测试、Git、系统命令。
- 浏览器 / Web 工具：检索、打开网页、提取动态内容。
- 视觉工具：识别截图、图片、版式问题。
- 消息工具：把结果发送到常用平台。
- 定时任务工具：定期检查、提醒、汇总。
- 子 Agent / 多 Agent 工具：把复杂任务拆给多个独立执行者。

但工具越多，风险越高。关键是定义清楚权限边界：

- 哪些目录可以改。
- 哪些命令需要谨慎。
- 什么时候可以 commit。
- 什么时候不能 push。
- 哪些源目录只能复制不能移动。
- 哪些事实必须查证不能凭记忆回答。

### 5. 从一个高频工作流开始创建

创建自己的 Agent 不要从“大而全系统”开始，而要从一个真实工作流开始。

例如：

1. 我给 Agent 一个链接或本地资料。
2. Agent 判断它属于 AI-Master 的哪个 raw 目录。
3. Agent 复制或生成 Markdown，不破坏原始来源。
4. Agent 更新 source-manifest。
5. Agent 如有整理价值，再创建 wiki 页面。
6. Agent 更新 index 和 log。
7. Agent 自检 frontmatter、路径、tag、链接。
8. Agent git add + commit，但不 push。

当这个流程反复跑通，Agent 就不再只是聊天助手，而开始成为我的知识生产流水线。

## 二、如何进化这个 Agent

### 1. 把每次纠正变成系统更新

Agent 进化的核心机制，是“纠正不要只停留在这一次”。

如果我指出：

- 不要主动 push。
- raw 源目录不能移动。
- 文件名不要用拼音。
- 业务文档不要写成概览。
- Agent 相关英文目录不要翻译。

那么这些纠正应该进入合适的位置：

- 长期偏好：写入 memory。
- 项目规范：写入 SCHEMA.md。
- 可复用流程：写入 skill。
- 单次任务记录：写入 wiki/log.md。

这样，Agent 才能从“被动听话”进化成“越来越懂我的系统”。

### 2. 把成功流程沉淀成技能

Agent 的技能库，是个人 Agent 进化最重要的资产之一。

一次复杂任务完成后，如果其中包含：

- 多个工具调用。
- 固定目录规则。
- 容易出错的路径。
- 特定命令组合。
- 用户明确纠正过的偏好。
- 可复用的检查清单。

就应该沉淀成 skill。

技能应该包含：

- 什么时候触发。
- 前置检查。
- 标准步骤。
- 常见坑。
- 验证方法。
- 输出格式。

这会让 Agent 的能力从“模型能力”变成“我的流程能力”。

### 3. 用知识库增强 Agent，而不是只依赖上下文窗口

上下文窗口再大，也不应该承担所有记忆。

长期知识应该进入知识库：

- raw 保存来源和原始材料。
- wiki 保存整理后的观点、概念、实体、方法论。
- SCHEMA 保存结构规范。
- index 保存导航。
- log 保存变更轨迹。

这样，Agent 在未来回答问题时，可以先检索知识库，而不是靠模糊记忆。

我理想中的 Agent 应该会主动问自己：

- 这个问题以前是否处理过？
- 相关资料在 raw 还是 wiki？
- 当前结论有没有来源？
- 是否需要更新某个页面？
- 这次流程是否值得沉淀为 skill？

### 4. 建立评估和复盘机制

Agent 不能只看“有没有完成任务”，还要看完成质量。

可以用几个维度评估：

- 正确性：事实是否查证，引用是否准确。
- 完整性：是否覆盖用户要求的所有细节。
- 可追溯性：是否保留来源、路径、hash、log。
- 可复用性：是否沉淀为 wiki、skill 或模板。
- 安全性：是否避免误删、误移、误 push。
- 风格一致性：命名、目录、frontmatter、中文表达是否符合我的习惯。

每次 Agent 犯错，都应该判断：

- 是缺少记忆？
- 是缺少 skill？
- 是 SCHEMA 规则不清？
- 是工具验证不足？
- 是 prompt 没说清？

然后把问题修到系统里，而不是只修当前结果。

### 5. 让 Agent 从单 Agent 进化到 Agent 组织

个人 Agent 的下一步，不只是一个 Agent 更强，而是多个 Agent 分工。

可能的分工：

- 主 Agent：理解我的目标，拆解任务，做最终判断。
- 研究 Agent：搜索资料、读论文、找证据。
- 写作 Agent：生成结构化文章、笔记、说明文档。
- 编程 Agent：改代码、跑测试、做 code review。
- 校对 Agent：检查事实、格式、链接、frontmatter。
- 监控 Agent：定时追踪信息源、GitHub repo、RSS、模型发布。

主 Agent 不一定亲自做所有事，而是像项目经理一样调度子 Agent，并最终把结果合并到我的知识库和工作流里。

## 三、如何用这个 Agent

### 1. 把 Agent 当成执行者，而不是搜索框

如果只是问“什么是 Agent”，它的价值有限。

更好的使用方式是给它任务：

- “把这个网页导入 AI-Master，并按 SCHEMA 整理 raw 和 wiki。”
- “检查这个仓库最近的改动，跑测试，给我提交中文 commit。”
- “帮我把今天关于 AI 的想法整理成一篇观点笔记。”
- “比较这三个工具，给出适合我知识库体系的选择建议。”
- “把这次踩坑沉淀成 skill，下次自动按这个流程来。”

也就是说，我应该尽量给 Agent 一个可完成、可验证、可沉淀的任务。

### 2. 给 Agent 清晰的输入、边界和验收标准

一个好的 Agent 指令应该包含：

- 目标：最终要产出什么。
- 范围：在哪个目录、哪个项目、哪个主题内操作。
- 约束：不要做什么，例如不要 push、不要移动源目录。
- 标准：什么叫做完成，例如文件创建、manifest 更新、测试通过、commit 完成。
- 偏好：命名、语言、深度、格式。

如果任务足够明确，Agent 就可以少问、多做、做完自检。

### 3. 把 Agent 用在持续性任务上

Agent 最适合做持续性任务，而不是一次性闲聊。

例如：

- 持续维护 AI-Master。
- 持续跟踪 AI Agent 技术栈。
- 持续把外部资料转成自己的知识。
- 持续记录我的判断、假设和复盘。
- 持续把复杂流程变成 SOP。
- 持续把项目经验沉淀为可复用资产。

Agent 的价值会随着使用次数增加，因为它会积累：

- 我的偏好。
- 我的资料。
- 我的流程。
- 我的命名体系。
- 我的历史决策。
- 我的长期目标。

### 4. 不要把所有判断都交给 Agent

个人 Agent 应该增强我，而不是替代我的判断。

我需要自己保留几个关键权力：

- 方向判断：什么值得长期投入。
- 价值判断：什么内容应该进入知识库。
- 风险判断：哪些操作不能自动化。
- 最终判断：哪些结论可以采纳。
- 审美判断：文档、图形、表达是否符合我的标准。

Agent 可以提出方案、执行流程、整理证据，但最终的“为什么做”和“做到什么程度”，仍然应该由我决定。

## 四、我的个人 Agent 蓝图

### 1. 输入层

输入可以来自：

- 我的一句话想法。
- 网页链接、文章、视频、播客。
- 本地 PDF、HTML、MHT、Markdown。
- Git 仓库、代码 diff、issue。
- Obsidian 知识库现有页面。
- 定时任务抓取的信息源。

### 2. 处理层

处理流程包括：

1. 判断任务类型。
2. 加载相关 skill。
3. 检索 memory、session、知识库和项目规则。
4. 制定短计划。
5. 调用工具执行。
6. 自检结果。
7. 需要时更新 raw/wiki/schema/log/skill/memory。
8. 需要时 git commit，但不默认 push。

### 3. 输出层

输出不应该只有聊天回复，还应该包括：

- raw 原始资料。
- wiki 整理页。
- source-manifest 清单。
- log 变更记录。
- Git commit。
- skill 文档。
- 可继续追踪的问题列表。

### 4. 进化层

Agent 每完成一次任务，都应该判断是否要更新：

- memory：稳定偏好和环境事实。
- skill：可复用流程和踩坑。
- SCHEMA：项目结构和规则。
- wiki：长期知识和方法论。
- prompt/persona：沟通风格和执行纪律。

这样，Agent 的成长路径就不是“模型升级”，而是“个人系统升级”。

## 五、下一步可以继续细化的问题

- 我的个人 Agent 应该优先服务哪些高频场景？
- 哪些任务可以自动执行，哪些必须确认？
- AI-Master 中 raw 和 wiki 如何更好承载 Agent 进化记录？
- 是否需要为“个人 Agent 方法论”创建 wiki 观点页或 playbook？
- 是否要建立 Agent 使用日志，用来复盘每次任务质量？
- 哪些 skill 是我最应该优先沉淀的？
- 多 Agent 分工时，主 Agent 和子 Agent 的边界怎么划？
